# 项目章程 — 中国大陆企业 Hermes Agent 原生管理系统

- 版本：v1.0
- 日期：2026-10-15
- 来源：templates/PLAN.md v2.0
- 状态：已由项目所有者逐块确认（目标/用户/范围/约束/假设/验收/风险/开放决策）

## 问题与目标用户

**要解决的问题：**

- 业务记录分散在 Excel/Word/PDF/聊天记录；
- 报销、采购、库存、审批缺少统一状态与审计；
- 员工缺少统一的业务发起入口；
- AI 对话与正式财务系统（金蝶）之间没有受控连接。

**目标用户与场景：**

- 普通员工：用微信等渠道以文字/语音/图片/文件发起报销、查进度、收退回补件通知；
- 主管：在授权范围内审批、拒绝、要求补件；
- 财务经办与财务主管：复核票据与金额、处理查验、导出报销单与明细；
- 仓储/采购：第二期进销存的入库/出库/盘点；
- 系统管理员：管理员工、角色、身份绑定与 Profile 生命周期，但不自动获得财务审批权；
- 审计人员：只读审计与查询。

**规模与范围：** 20–100 名员工，首期仅中国大陆部署。

## 目标与非目标

**目标（首期）：**

- 以 Agent 为主要工作入口；
- 每人独立 Hermes Profile 与独立进程；
- 渠道与 Agent 进程解耦；
- 报销全流程闭环；
- 审批任务路由与通知；
- 标准化文档/表格输出；
- 最小管理后台；
- 审计与备份恢复。

**非目标（首期）：**

- 不自行开发完整会计引擎；
- 不执行付款；
- 不做进销存（第二期）；
- 不做多租户/跨机协作/远端 Issue-PR-CI；
- 不绕过金蝶正式 API 或许可机制；
- 不绕过官方发票查验平台的访问控制；
- 不把 Agent 记忆当作业务记录；
- 不向业务 Agent 开放任意 SQL 或任意 shell。

## 关键约束与强制原则

**强制原则（沿用 templates/PLAN.md §1.1）：**

- 每人一个 Hermes Profile、独立进程与独立配置/记忆/会话/技能上下文，不同员工不得共用同一 Profile；
- 通讯渠道与 Agent 进程解耦，每条消息必须路由到正确的员工 Profile；
- 正式业务数据写入统一业务数据库，Agent 记忆只用于对话连续性；
- Hermes 不直接持有数据库管理员权限，不提供任意 SQL 或任意服务器命令作为普通业务工具；
- 所有读取、写入、审批、导出、文件下载与外部同步均由后端执行权限验证并写入审计；
- 模型只能提取、解释、建议、生成草稿，金额计算、库存计算、会计校验、审批状态转换与付款状态必须由确定性程序或外部系统驱动；
- 普通微信是首个渠道而非永久绑定渠道；
- 中国大陆是首期唯一目标运行范围。

**工程约束：**

- 本机（2 vCPU / 1.9 GiB 内存）仅作编排与开发机，生产 Profile 主机另行准备；本机虽已配置 swap（/swapfile 2 GiB + zram0 约 986 MiB，合计约 3.0 GiB，2026-10-15 22:41 实测），但 swap 不作为常驻 Agent 容量依据；生产主机为同类 Debian Linux，内存更多、CPU 更快（具体规格待定，见 O1）。
- 本地并行执行实例上限为 1；
- 业务代码位于本仓库 app/ 下（11 个领域目录已建立）；
- Master 不实现产品代码，只做调度、审查、合并；
- 关键状态与决策写入本地任务库与任务记录。

**数据处理约束：**

- 部署、附件与备份优先位于中国大陆可控环境；
- 云端模型优先选择能明确提供大陆服务区域与数据处理条款的供应商；
- 按任务最小化传给模型的字段并对敏感字段遮蔽或去标识化；
- 未完成合规评估前不把跨境传输视为默认许可。

**验证约束：**

- 一切验收必须有真实命令输出与退出码；
- 未建立的验证命令写“待建立”并登记任务，不得声称通过。

## 假设（需验证）

- A1 金蝶产品、版本、部署方式与 API 许可未知，需阶段 0 确认。
- A2 当前不存在可面向任意企业调用的公开发票查验 API，先按人工辅助流程设计。
- A3 普通微信作为首渠道存在稳定性、合规与主动通知的不确定性，由 W0-1 给出 Go/No-Go 结论。
- A4 本机无法承担负载验收，容量结论必须在生产主机取得。W0-7 实测：内存不是本机的绑定约束（空闲口径下 20–30 个被服务 Profile 约需 1.3–1.4 GB），真正的约束是 2 vCPU、所有 Profile 挤在同一网关进程的共享命运，以及活动负载成本未测。
- A5 内存模型已按实测修正：单网关进程是共享基线（实测 RSS 426952 kB / Pss 421931 kB），多路复用下每新增一个空闲被服务 Profile 的边际内存约 14 MB（实测 13.2 / 13.1 / 15.8 MB），不随 Profile 数线性放大（解释器、模块与内置技能在同一地址空间内共享）。405–409 MB 是共享基线而非每 Profile 边际值；活动负载下的每 Profile 增量未测，须在生产主机以真实负载复测（W0-7 §4）。
- A6 规则包文件已纳入版本控制，worktree 隔离可用（不在此记录具体 head，避免陈述过期）。
- A7 提交作者沿用仓库级占位值 Agent Orchestration <agent@localhost>（项目所有者已决定不更换）。
- A8 多路复用运行时凭据 fail-closed 与活动负载内存曲线尚未实测（W0-7 §5.3、§7）；测试 Profile profile-a/b/c 现由默认网关服务，清理命令见 W0-7 §7.1。

## 初始成功标准与验收

- 至少 3 个测试员工走通完整报销闭环（创建→提交→审批→财务复核→导出）。
- 员工 Profile/进程/配置/记忆/文件目录互相隔离，跨员工访问测试全部被拒绝。
- 未绑定或已解绑的渠道身份默认拒绝。
- 重复消息与重试不重复创建报销单或审批任务，幂等可复现。
- 金额、日期、必填字段异常被拒绝或要求人工确认。
- 主管不能批准自己的报销。
- 权限拒绝、状态变化、导出、外部调用均可审计。
- 数据库与附件备份可在生产主机之外恢复，并完成真实恢复演练。
- 在生产主机上完成首期 20–30 用户规模的并发容量结论（含真实活动负载下的内存与 CPU 曲线）；100 用户作为后续扩容目标。

## 风险与缓解

- R1 个人微信通道不可用或不稳定 → 渠道适配层与业务域解耦，先出 Go/No-Go 报告，必要时换企业微信/钉钉/飞书/邮件，不阻断业务架构。
- R2 金蝶接口条件不明或不可写 → 先落 KingdeeAdapter 接口，只读连接先行，写操作仅推送草稿且带幂等键。
- R3 20–30 个常驻 Profile 的资源成本 → 生产主机以真实活动负载做容量规划（W0-7 实测空闲边际约 14 MB/Profile，但活动负载未测）；本机 2 vCPU 与单网关共享命运是主要约束；不得未经批准改为共用同一 Profile。
- R4 发票查验无官方或授权接口 → 人工辅助流程，状态机严格区分 OCR 识别与查验通过。
- R5 双系统数据权威冲突 → 每个财务领域在决策记录中指定唯一权威源，禁止两边各自独立维护同一余额。
- R6 数据合规与跨境传输风险 → W0-5 交付字段级数据分类与供应商条款审查清单。
- R7 权限与越权风险 → 后端每次调用执行授权，并配套负面测试（越权、非法状态、并发冲突、失败恢复）。
- R8 并行 Agent 编辑冲突 → 路径锁与领域目录所有权，并发上限 1。

## 架构决策与替代方案

- D1 每人独立 Hermes Profile 与进程（替代：共用 Profile —— 已否决，因隔离与审计要求）。
- D2 共享渠道接入与身份路由服务（替代：每个 Profile 各自登录同一微信 Bot —— 已否决，账号限制且不可维护）。
- D3 模块化单体 FastAPI + PostgreSQL + Alembic（替代：SQLite 作为生产库 —— 已否决；微服务 —— 现阶段过度设计）。
- D4 领域目录所有权：app/{identity,intake,expense,workflow,documents,inventory,integrations,audit,api,db,core}，一个任务只锁自己的领域目录（已由 TASK-0001 落地）。
- D5 事务性 Outbox 与 Worker 处理通知和外部同步（替代：直接同步调用 —— 会丢事件或产生重复）。
- D6 正式账务留在金蝶，内部系统负责对话入口、原始资料、审批与协同（替代：自建会计引擎 —— 已否决）。
- D7 交付证据链：Git 分支 + head SHA + 真实命令输出，Master 独立复核后以 --no-ff 合并。

## 开放决策（需所有者输入）

- O1 生产 Profile 主机规格与数量（影响阶段 0 负载验收与阶段 1 验收标准）—— 所有者已确认：生产主机为同类 Debian Linux，内存更多、CPU 更快，具体规格待定。按 W0-7 实测，内存不是首要约束（空闲口径 20–30 Profile 约需 1.3–1.4 GB），规格应以真实活动负载测试结果为准；本机 2 vCPU 与单进程共享命运才是现实约束。
  - 选项：(a) 自建物理或虚拟服务器（大陆机房，Debian 系）；(b) 大陆区域云主机（Debian 系），按 Profile 数弹性扩容；(c) 先以 20–30 人规模上线，据真实负载再扩容。
- O2 金蝶产品、版本、许可与测试账套（影响阶段 3 全部工作）—— 建议由公司财务与金蝶客户经理确认后提供。
  - 选项：(a) 金蝶云星空 OpenAPI；(b) 金蝶云苍穹；(c) KIS / 精斗云或其它产品；(d) 暂不接入，仅先跑内部流程。
- O3 发票查验的授权渠道（影响发票状态机与人工辅助流程规模）—— 建议先按人工辅助落地，同时询问金蝶或服务商是否提供授权接口。——已决策（2026-10-16）：首选=百度智能云『增值税发票验真』；腾讯云与聚美智数降为备用（仅注释/文档留痕，不做事先可选项）；manual_assisted 兜底保留。
  - 选项：(a) manual_assisted 人工辅助流程（先落地）；(b) authorized_provider，金蝶或经批准服务商的授权接口；(c) official_api，取得官方文档与合法授权后再实现。
- O4 数据权威边界：库存与账务分别由哪个系统唯一决定（影响阶段 2/3 数据模型与对账）—— 建议内部系统为报销流程权威源、金蝶为已过账凭证权威源，库存权威源待阶段 0 确认。
  - 选项：(a) 内部系统为报销流程权威源、金蝶为已过账凭证权威源；(b) 全部以金蝶为权威源，内部只产出草稿；(c) 库存与账务分别指定不同权威源（待阶段 0 定）。
- O5 模型供应商与模型侧安全 —— 已决策：由项目所有者自行把控，不作为本项目的阻塞项或验收项；本项目只负责按字段白名单控制送入模型的数据（W0-5 §3）。
- O6 脱敏业务样例的提供方式与存放位置（影响 W0-6 与解析流水线设计）—— 建议脱敏后置于仓库外的受控目录，仓库内只保留字段清单与模板。
  - 选项：(a) 脱敏后置于仓库外受控目录，仓库内只留字段清单与模板；(b) 仓库内 samples/ 目录且强制脱敏与访问受限；(c) 不提供真实样例，改用合成数据。
- O7 templates/PLAN.md 的最终归位 —— 已决策：保留在当前位置，不恢复通用模板；同时记录 validate_kit.py 的必需文件清单依赖该路径，不得移动或删除。

## 初始里程碑

- **最小垂直切片：** 单个测试员工通过本地 Hermes Profile 以文本提交一笔报销（含一张附件），后端校验后生成草稿、创建审批任务，主管审批通过，导出 PDF/XLSX，全程可审计查询。
- **验证方式：** 真实命令输出与退出码；包含越权与重复消息的负面测试。
- **回退：** 数据库迁移可回滚；分支未合并即可丢弃；附件与草稿区可整体清理。
