# AgentMgr：独立 Agent 治理与企业决策服务

- 版本：v1.0（架构基线草案，须经 Phase 0 冻结）
- 用途：可由全新仓库独立采用的产品与实施规格
- 推荐起步技术栈：Python 3.13、FastAPI、Pydantic、PostgreSQL、SQLAlchemy、Alembic；远程 MCP 使用官方 Python SDK 的稳定版本
- 首期假设：中国大陆企业内部部署、单企业实例、20–100 名员工；预留组织边界但不在 MVP 实现 SaaS 多租户
- 状态：目标与方向已由项目所有者提出；接口、状态机与安全模型须在 Phase 0 验收后冻结

## 1. 产品定位与原则

AgentMgr 是独立的 Agent 治理与企业决策服务，不是某一个 Agent 框架的管理面板，也不重新开发 WorkBuddy、Hermes、Rakazo、Codex、OpenCode 等已经具备的命令行、文件读写、浏览器控制、软件连接器、模型推理或通用 Agent 规划能力。

AgentMgr 的价值集中在执行前、中、后的关键关口：是否需要做、优先级如何、谁负责、谁有权做、允许哪些能力、禁止哪些行为、哪些前置条件必须满足、何时需要澄清/确认/审批、执行结果如何验证、出现失败时由谁接手。

### 1.1 不可妥协的设计原则

1. **不重复造工具链。** Agent 运行时已有 CLI、浏览器、文件和连接器能力时，AgentMgr 管理这些能力的授权与边界，不再自行实现平行版本。
2. **策略确定性执行。** 模型可提出目标、解释理由或建议优先级，但不能自报身份、角色、责任人、权限、审批结果或最终授权。
3. **策略判定必须落到执行点。** 提示词、工具描述、Agent 的自我约束或事后审计都不是强制安全边界。企业资源和有副作用的动作须经过策略执行点（PEP），或由 OS 身份、隔离环境、网络出口、短期凭据与受控代理形成不可绕过的边界。
4. **能力不等于权限。** 一个运行时可以有 Shell 工具，不代表某员工或任务有权用它访问任意数据、文件或生产系统。
5. **职责分离。** Requester、Accountable Owner、Assignee、Executor、Approver 和 Service Identity 分别表示，不合并为一个 agent_id。
6. **优先级不提升权限。** 高优先级可影响调度顺序、SLA 和升级，但不能覆盖硬性拒绝、数据范围、确认/审批或安全边界。
7. **最小权限、短时授权、可撤销。** 执行授权绑定任务、主体、能力、资源范围、策略版本、有效期和预算/调用上限。
8. **任务记录归服务所有。** 任务状态、审批、授权、执行证据和审计保存在 AgentMgr 或正式业务系统，不以 Agent 记忆或对话历史作为权威记录。
9. **模块化单体优先。** 先在一个可独立部署的服务内按领域分层；有明确容量或隔离依据后再拆服务。
10. **协议与运行时分离。** MCP 是客户端/工具接口协议，不自动成为所有 Agent 的远程任务控制协议。Hermes、Rakazo 等通过内部 Runtime Adapter 契约接入。
11. **失败关闭。** 身份、策略、资源范围或契约无法确定时，不执行有副作用的动作。
12. **现有业务能力不复制。** 已有 RBAC、业务状态机、工作流、文件、审计和 Outbox 能力优先复用；本计划不要求推翻这些资产。全新仓库没有这些资产时，按本计划从零建立等价能力，不假定其已存在。

## 2. 决策关口

每个任务进入执行前，服务至少应能记录以下问题的机器可判定结果：

- **必要性：** 是否需要执行；目标是否已满足、任务是否重复、是否缺少关键输入。
- **优先级：** 排序、截止时间、SLA、成本预算、资源上限和升级条件。
- **责任：** 谁发起、谁对业务结果负责、谁执行、谁审批、失败后谁接手。
- **允许事项：** 哪些能力、数据范围、业务动作、系统和资源可用于目标。
- **禁止事项：** 禁止操作、资源、路径、网络、软件、数据类别与副作用。
- **前置条件：** 澄清、用户确认、主管审批、双人复核或额外结果验证。
- **执行模式：** 客户端建议模式、企业资源受控模式、受控服务器端执行，或拒绝。
- **完成定义：** 如何验证结果、部分成功、失败、回滚与人工接管。

自然语言不是生效策略。策略需映射成有版本的规则、能力、资源范围和明确的决策结果。

## 3. 目标、范围与非目标

### 3.1 MVP 目标

1. 建立人员/服务主体、角色、部门、资源范围、能力目录和版本化策略。
2. 接受结构化任务请求，校验请求身份、目标、优先级、责任与必要上下文。
3. 返回 allow、deny、needs_clarification、needs_confirmation、needs_approval 或 managed_execution_required 等机器可判定结果。
4. 对允许执行的任务创建有范围、有期限、可撤销的 Execution Grant。
5. 通过 MCP 与 REST 提供受控治理工具、任务查询和管理接口。
6. 持久化任务、任务事件、负责人、优先级、审批、策略版本、运行时 ID、结果及审计关联。
7. 通过 Runtime Adapter 启动/查询/取消服务器端 Agent 任务，并如实记录每个运行时不支持的能力。
8. 支持幂等、确认/审批绑定 payload hash、TTL、重复执行防护、失败恢复及人工接管。
9. 提供最小管理 API 或界面，用于策略配置、任务分派、审批、审计和故障处置。
10. 用统一契约和共同测试支持不同 Agent 或不同团队并行独立实现并进行差异比较。

### 3.2 MVP 非目标

- 重造通用命令行、浏览器、文件管理、办公软件连接器、数据库客户端或 Agent 规划/记忆系统。
- 训练模型、自建基础模型、实现万能软件操控器。
- 远程强制约束客户端本地已经可访问的任意 Shell、文件、浏览器或个人凭据。
- 一次性兼容所有 Agent、所有 MCP 扩展或多 Agent 协商协议。
- 无必要地拆成微服务，或默认引入 Kubernetes、Redis、Kafka 等基础设施。
- 提供万能 SQL、万能 Shell、任意 execute_action 或由模型自行生成并批准权限的接口。
- 自动执行付款、生产数据删除、不可撤回外发等高风险动作而无明确授权门槛。
- MVP 实现完整 SaaS 多租户；数据模型可预留 company_id 等组织边界。

### 3.3 三种运行模式必须在产品中区分

**A. 客户端/建议模式（Advisory / BYOA）**：用户当前使用的 Agent 连接 AgentMgr，获得策略建议、登记任务或调用受控业务工具；本地 Agent 的其他工具可能绕过治理。不得宣称本模式实现了本地操作的强制控制。

**B. 企业资源受控模式（Governed Resource Access）**：企业数据库、业务 API、文件存储和软件账号只允许经 AgentMgr 的 PEP 或同等受控代理访问；客户端 Agent 不能绕过访问企业资源。用于需要可靠的企业数据权限和审计的场景。

**C. 受控执行模式（Managed Execution）**：Agent 在服务器端运行于受隔离的服务账户/沙箱中，使用任务级凭据、受限文件系统、受限网络出口和运行时策略；用于需要约束 Shell、浏览器和文件操作本身的场景。

每个任务、界面、API 和审计记录必须标明执行模式及剩余风险。

## 4. 核心术语与策略模型

- **Principal**：经验证的用户、服务或运行时身份。
- **Requester**：任务发起者。
- **Accountable Owner**：对业务结果负责的人员/组织角色；必须可追责，不能以 Agent 名称替代。
- **Assignee**：负责推进工作的人员、Agent 或队列。
- **Executor**：实际执行任务的 Agent 实例或人工执行者。
- **Approver**：具有独立授权的审批人；遵守禁止自审等职责分离规则。
- **Delegation**：有范围、有期限、可撤销的受限委派。
- **Service Identity**：Agent/连接器访问资源所用的非人身份，不得充当绕过员工职权的管理员身份。
- **Capability**：可请求的动作类别，不代表其已被授权。
- **Resource Scope**：资源范围，如本人、部门、审批链、项目、指定目录或业务记录集合。
- **Policy**：根据主体、动作、资源、任务、风险和环境做出确定性判断的规则。
- **Execution Grant**：某次任务执行的授权快照，含策略版本、允许/禁止能力、资源范围、期限、预算、确认/审批引用和撤销状态。
- **PDP（Policy Decision Point）**：无副作用的确定性策略判定。
- **PEP（Policy Enforcement Point）**：在 MCP、REST、连接器、工具调用和资源访问时强制执行判定。
- **Runtime Adapter**：将内部任务契约映射到具体 Agent 运行时，不将运行时内部对象暴露给核心业务。

策略冲突时优先级为：系统/法律/安全硬拒绝 → 企业策略与数据分类 → 主体角色与资源范围 → 任务级授权 → 调度优先级/SLA/预算 → Agent 建议。低层不能覆盖高层拒绝。策略缺失、版本无效或授权服务不可用时 fail closed。

“必要性”允许 Agent 提供理由，但系统要确定性检查重复任务、已满足目标、权限缺失和必要字段缺失。模型分数只可用于排序建议，不得替代硬规则。

## 5. 目标架构与接口面

客户端：WorkBuddy / Codex / OpenCode / Web / 其他 MCP 客户端
→ MCP over HTTPS / REST
→ AgentMgr 模块化单体
→ PostgreSQL + 受控附件存储 + Outbox/Worker
→ Runtime Adapter
→ Hermes（首个候选）/ Rakazo（第二候选）/ 后续已验证 Agent 运行时
→ 受控业务工具和企业资源。

AgentMgr 服务至少包含：
- 身份认证和可信 Principal 解析；
- 版本化策略注册与发布；
- PDP 与 PEP；
- 任务/责任/优先级/确认/审批/委派；
- 工具契约目录、MCP/REST 适配层；
- Runtime Adapter 与 Worker；
- 执行事件、审计、指标、Trace；
- 管理 API 或最小界面。

接口面彼此区分：
1. **客户端 MCP**：评估/登记任务、查询状态、申请确认/审批、取消和查询结果。
2. **管理 REST**：人员角色、策略版本、任务分派、审计查询与运维诊断。
3. **服务端 Agent 业务工具 MCP**：为当前任务提供受限业务工具；每次调用重新授权。
4. **Runtime Adapter API**：AgentMgr 内部控制接口，负责提交、查询、事件/轮询、取消、输入等待、结果和健康检查。
5. **资源连接器/PEP**：企业资源尽量只可通过受控服务访问，阻断 Agent 从本地工具直接绕行。

MVP 用 PostgreSQL 持久化任务队列、租约和 Outbox；只有压力测试证明有必要时才增加外部消息系统。MCP 层负责协议转换和输入 Schema，不另建业务规则。

## 6. MCP 与 REST 工具契约

候选客户端工具：
- governance.evaluate_task：评估必要性、权限和执行模式，不产生副作用。
- governance.submit_task：创建通过校验的任务。
- governance.get_task / governance.list_my_tasks：按当前身份和范围查询任务。
- governance.request_confirmation / governance.request_approval：建立不同语义的确认或审批请求。
- governance.cancel_task：发出取消请求；不能虚报任务已经停止。
- governance.get_result：返回已授权的结果摘要和证据引用。

服务端 Agent 工具按具体业务能力命名，不提供任意 SQL/Shell。每项工具至少定义：
- name + version + input/result schema；
- 描述、适用和不适用场景；
- 所需权限、资源 scope 与字段来源；
- 风险级别、副作用、确认/审批策略；
- 幂等策略、执行 handler、审计动作与错误码。

可信身份、owner、approver、已验证金额、政策版本等由服务端解析；模型可提供的字段必须重新校验。禁止把客户端 MCP、服务端业务工具 MCP、运行时管理 API 共用一个无限制管理员 Token。

统一结果应区分成功、需要澄清、待确认、待审批、未认证、禁止、无资源、参数错误、冲突、运行时不支持、超时、状态未知和内部错误。长任务先用持久化 task_id + 状态查询实现；只有真实端到端验证后才承诺事件流。MCP Tasks 扩展不是所有客户端/运行时必备能力，不能当作默认基础。

所有公开契约版本化。破坏性 Schema 变更需升主版本或提供兼容过渡；审计记录工具版本和策略版本。

## 7. 核心数据模型

最小模型集合，最终表结构由 Phase 0 冻结：
- identities / principals：人员与服务主体、状态、外部身份绑定；
- roles / capabilities / role_capabilities：岗位职权与可请求动作；
- policies / policy_versions：策略定义、发布与回滚版本；
- tasks：目标摘要、状态、priority、due_at、SLA、requester、owner、assignee、executor、approver、执行模式、policy_version、idempotency_key；
- task_events / task_attempts：状态转换、重试、进度、取消、错误和证据关联；
- execution_grants：主体/任务/能力/资源范围、TTL、预算、版本、撤销状态；
- confirmations / approvals：payload hash、申请人与审批人、过期时间、一次性消费和决策记录；
- runtime_instances：运行时类型、能力快照、外部任务 ID、连接状态与版本；
- audit_events：不可篡改式审计事件；
- outbox_events：保证任务事务与后续调度一致；
- connector_credentials 或 credential_refs：只保存安全引用，不保存明文秘密。

同一主体的业务权限来自可信认证与策略，不从模型参数推导。服务端运行时凭据应尽量任务级、短时且可撤销。

## 8. 任务生命周期、优先级与幂等

建议状态：
draft → evaluated → awaiting_clarification / awaiting_confirmation / awaiting_approval → queued → dispatched → running → verifying → succeeded。
异常终态/分支至少含 denied、cancel_requested、cancelled、failed、timed_out、needs_human、partial_success、unknown。

状态机规则：
- 每次转换由确定性服务验证并写入 task event；
- 取消请求与运行时实际停止是不同状态；
- 超时或提交返回不明时先查询运行时，不盲目重发创建请求；
- Worker 通过租约/抢占恢复任务；重试前检查该动作是否可安全幂等；
- 完成与否以验证规则和结果证据为准，不直接接受 Agent 的“我完成了”声明；
- 写操作使用幂等键；确认绑定规范化 payload hash、TTL 和一次性消费；执行前重新校验权限与状态；
- 负责人、审批人缺失或职责冲突时拒绝；
- 高优先级必须有授权及理由，不能改变安全决策。

排序建议考虑优先级、截止时间、SLA、资源需求和公平性，避免高优先级任务永久饿死普通任务。优先级算法必须可解释并有测试。

## 9. Runtime Adapter 与运行时接入

内部接口至少包括：
- capabilities()：报告支持能力与版本；
- submit_task(task, grant)；
- get_status(runtime_task_id)；
- poll_events(runtime_task_id) 或订阅事件（若支持）；
- provide_input(runtime_task_id, input)（若支持）；
- cancel_task(runtime_task_id)；
- get_result(runtime_task_id)；
- health()。

适配器应将外部状态映射为内部状态，并明确“不支持”“请求已受理”“已停止”“状态未知”等差异。核心业务不得依赖 Hermes/Rakazo 私有对象、数据库 schema 或个人 Profile 路径。

**Hermes 为首个候选运行时**：先验证可公开、稳定使用的 Run/任务 API、认证、持续事件、取消、任务隔离、结构化结果、任务级工具权限和凭据注入。允许使用其已支持且经验证的 HTTP API；不能因为存在 MCP Server 就推断它是通用远程执行入口。

**Rakazo 为第二候选运行时**：先做只读兼容性 Spike，核对提交/状态/结果/取消/输入等待、服务端部署、安全隔离和认证。只有稳定接口通过契约测试后才开发适配器。若适配 Rakazo 需要修改核心业务/授权/状态机，应先审查契约是否设计错误。

## 10. 安全与治理控制

每次执行必须：
1. 认证 Principal，拒绝停用、解绑或来源不可信的主体；
2. 检查任务状态、owner/assignee/executor/approver 分离规则；
3. 验证 capability、resource scope、数据分类和策略版本；
4. 检查执行 Grant 是否绑定当前任务、未过期、未撤销且范围未被扩大；
5. 应用澄清/确认/审批门禁；
6. 将执行限制落实到 PEP 或运行环境；
7. 记录决策、执行结果和对应审计关联。

必须覆盖的安全机制：
- PDP 与 PEP 区分；PEP 在每次敏感调用执行授权，不能只在任务开始时检查一次；
- Grant 范围、TTL、撤销、预算、策略版本和工具版本；
- 高风险动作的显式确认或独立审批；禁止自审；
- 服务账号最小权限、独立 UID/运行账户、文件系统限制、独立临时目录、网络出口限制；
- 凭据只注入执行环境，不进提示词、Trace、Git 或普通日志；
- 限流、并发/CPU/内存/时间上限、取消/终止和审计；
- 默认拒绝、策略服务不可用时 fail closed、管理变更留痕；
- 审计和诊断 Trace 分开，日志不保存不必要的原始文件、令牌或个人数据。

### 10.1 客户端治理的明确限制

远程 MCP 只能治理经过该服务的调用。客户端 Agent 若持有本地高权限 Shell、浏览器会话、共享盘或 API 密钥，仍可能绕过 AgentMgr。因此：
- Advisory 模式只提供建议与受控工具，不宣称强制治理本地全部操作；
- 企业资源受控模式要通过 ACL、防火墙、凭据管理及连接器限制资源直连；
- 受控执行模式须采用隔离服务账户/沙箱、短期凭据和网络出口规则；
- 若某项约束无法技术强制，必须记录剩余风险并限制相应的安全承诺。

## 11. 审计、隐私与可观测性

审计至少关联 request_id、task_id、已验证 actor、owner、assignee、executor、approver、policy_version、grant_id、tool_name/version、资源引用、决策与原因码、确认/审批结果、运行时 ID、执行结果、时间戳和幂等状态。

审计回答“谁在什么授权下对哪个资源做了什么”；Trace 回答“技术调用经过哪些阶段”。二者分开存储和保留策略。不得把令牌、密码、API Key、完整票据或无必要个人信息放进审计和提示词。拒绝和失败也要记录，但需避免泄漏受保护数据。

## 12. 测试与验收标准

### 单元与契约
- PDP 同输入、同策略版本返回可复现决策；
- JSON Schema/类型契约有正向和负向 fixtures；
- 每个状态转换都有允许与拒绝用例；
- 各 Runtime Adapter 共用测试套件；
- REST 与 MCP 走相同应用服务和业务授权，不复制规则。

### 安全负向
- 未认证、伪造身份、停用/解绑主体、无权限、资源越界；
- 高优先级试图绕过硬拒绝；
- 过期/撤销 Grant、策略版本不符、运行时服务身份权限扩大；
- 自审、缺负责人、审批绕过、确认重放、payload hash 不符；
- 重复任务、并发重复副作用、取消竞态、提交超时后状态未知；
- Agent 试图访问隔离目录、未授权网络、他人文件或凭据；
- 日志/Trace/错误响应泄露凭据或敏感字段。

### 端到端
1. 已认证员工提出任务，系统评估并澄清缺失信息；
2. 任务明确必要，分配 owner/assignee，按策略进入确认或审批；
3. 获准任务创建 Grant 并由服务器端 Agent 执行；
4. Agent 调用受控业务工具，每次调用重新校验；
5. 系统验证最终结果、记录证据并审计；
6. 人工取消、运行时崩溃、策略撤销或资源服务失败时，进入正确状态且可恢复；
7. 至少一个真实客户端、一个真实运行时完成可复现链路；Mock 证据单独标记，不能冒充真实兼容性。

验收证据必须含当前提交 SHA、真实命令/退出码、CI 对应 SHA、测试结果和未解决风险。不能通过删除或弱化既有断言取得通过。

## 13. 部署与运维

- MVP 可由一套 AgentMgr API、PostgreSQL、附件存储、Worker 和一个受隔离的 Agent 运行时节点组成。
- 生产秘密由 Secret Manager 或权限受限的环境注入；不得提交到仓库或写入任务提示。
- 服务到数据库使用最小权限运行账号；数据库迁移使用独立 DDL 身份。
- 企业数据和备份按部署地/法规与组织要求保存；具备加密、访问审计、保留期及恢复演练。
- 监测任务积压、超时、重试、运行时不可用、策略拒绝率、Grant 撤销失败和 Worker 租约过期。
- 运行手册必须说明任务卡住/未知状态、运行时升级、凭据撤销、备份恢复、审计检查、紧急停止和手动接管流程。
- 不在未测量前承诺吞吐量或并发上限；通过目标部署环境的真实活动负载测量容量。

## 14. 分阶段可执行路线图

### Phase 0 — 产品与契约冻结
交付：ADR、术语/责任模型、PDP 结果 Schema、任务/Grant/确认模型、任务状态机、Runtime Adapter 契约、MCP/REST 契约、威胁模型、运行时能力调研、两种并行开发方法与固定验收集。

验收：合法/非法 JSON fixtures 可验证；每个状态转换有定义；至少 15 项威胁及对应负向测试；明确客户端绕行风险；运行时能力标注“已验证/部分验证/未验证”；产品负责人确认前不得并行开发互相依赖的产品实现。

### Phase 1 — 服务骨架、身份与审计
建立模块化单体骨架、认证 Principal、权限目录、统一错误格式、迁移/测试/CI 和不可变审计策略。验收包含服务主体、用户主体、停用和撤销路径的负向测试。

### Phase 2 — 策略决策与任务生命周期
实现 PDP/PEP、能力目录、任务/责任/优先级、Grant、确认/审批、幂等、Outbox/Worker、恢复和取消。验收所有安全门禁均由测试证明，不依赖提示词。

### Phase 3 — 客户端 MCP + REST
提供治理工具、任务提交和查询、确认/审批申请与取消；先只读后受控写入。验收真实远程 MCP 客户端、REST 客户端和同一套授权结果。

### Phase 4 — 首个服务器端运行时
实现 Runtime Adapter 与 Hermes 接入；完成提交、状态、进度、取消、结果、故障恢复和受控业务工具调用。所有不支持语义记录于兼容性报告。

### Phase 5 — 执行边界与安全加固
部署受限运行环境、服务身份、任务级凭据、网络和文件系统限制；完成绕行负向测试、撤销、审计与恢复演练。这一阶段是对外宣称“受控执行”的前置条件。

### Phase 6 — 第二运行时与可移植性
对 Rakazo 做 Spike 并按验证结果实现；运行共享 Adapter 契约和安全套件。第二运行时不得要求改动核心业务策略和任务状态机。

### Phase 7 — 企业试点与发布
在受控试点中验证真实工作流、容量、恢复、安全、运维告警和人员交接；所有未支持能力列入发布限制。通过前不得宣传为全面治理任意 Agent 的全部本地能力。

## 15. 多 Agent 并行开发和实现比较

### 15.1 从全新仓库独立启动
每个候选实现都收到同一份计划、契约版本/哈希、工具链限制、验收 fixtures 和统一启动提示。候选使用独立仓库/分支或 Worktree；不得读取另一个候选的实现细节后声称独立设计。

### 15.2 在同一仓库并行
Phase 0 冻结后，将任务拆为路径不重叠的垂直工作包。所有任务在 Issue 记录目标、允许/禁止路径、依赖、测试和证据；执行者不得批准/合并。公共契约、数据库迁移、依赖锁和安全核心变更必须由单个任务独占；全量测试通过部署方规定的串行测试闸门（如全量测试需独占测试库）执行。

### 15.3 比较矩阵
候选使用统一测试与 100 分评分：规格符合度 20、安全与越权控制 25、任务状态/恢复 15、接口契约质量 10、测试质量 15、可维护性 10、部署/运维说明 5。出现硬性越权、凭据泄露、审批旁路或数据越界时直接不合格，不因总分高而补偿。偏离规格必须书面列出，由统一决策同步到所有候选。

## 16. 全新项目启动提示词

你是新项目的技术负责人。仅以本计划及其冻结的 Phase 0 契约为权威规格，从空仓库开始实施 AgentMgr 独立 Agent 治理服务。不要假定存在旧代码、旧数据库、旧 CI 或已验证的运行时能力。先执行 Phase 0：输出 ADR、术语模型、数据模型、接口 Schema、状态机、威胁模型、架构图、阶段依赖和可运行测试 fixtures；禁止跳过契约冻结直接并行实现。优先复用成熟 Agent 的命令行、文件、浏览器及连接器，不重造轮子。所有授权由确定性服务判定，并在实际执行点实施；若环境无法阻断绕行，明确记录而非声称已治理。每个任务必须可测试、可审查、可恢复、可审计，报告真实验证命令和退出码。未经产品负责人批准，不自行变更安全边界或重大架构决策。
