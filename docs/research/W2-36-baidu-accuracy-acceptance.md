## 0. 一页结论

1. **端到端成功率 8/8，字段级「完全一致」率在 9 个可比字段上为 100%**：开票日期、
   价税合计金额、税额、发票号码、销方名称、销方税号、购方名称、购方税号，以及派生
   核对的不含税金额（`amount − tax_amount`），8/8 与真值精确一致（日期 ISO、
   金额两位小数）。
2. **唯一系统性错误是 `invoice_code`：8/8 全部偏离真值**——8 张均为数电票（无独立
   发票代码），解析器却为每张票产出一个 **2 字符、非数字的脏值**，且该字段置信度全部
   回退到 `0.5`。根因是提供商把该字段返回为**空数组**，适配器把空数组 `str()` 成
   字面量（见 §7 D1）。这是**本次唯一发现的解析缺陷**，不在本任务内修复。
3. **票种分类在「数电普票」这一层是准的，但粒度不足以区分业务类别**：8 张票
   （6 张旅客运输服务 + 2 张餐饮服务）**全部**分类为 `vat_invoice`。按「数电普票
   →`vat_invoice`」口径统计为 8/8；但百度 `invoice_type` **无法区分**
   「旅客运输服务」与「餐饮服务」——按票种设计「人工确认必填项」的需求不能只依赖
   `invoice_type`（见 §7 D2）。
4. **置信度整体偏高但保守**：72 个非票种字段置信度中位数 0.916、最低 0.5、11 个
   （15.3%）低于默认阈值 0.75；其中 3 个**金额字段取值完全正确却低于阈值**，
   8 个是 §7 D1 的回退值。**没有出现「高置信度但取值错误」的样本**。
5. **配额纪律达成**：实际只调用 `multiple_invoice` **8 次**（+ 1 次 OAuth token），
   全部 HTTP 200、0 次重试，远低于 12 次上限（见 §8）。

## 5. 置信度分布

取值口径为 W2-35 §2.1：`min` → `average` → `0.5`（本批 `probability=true` 生效）。

| 指标 | 值 |
|---|---|
| 归一化字段总数 | 80（含 8 个 `invoice_type` 分类置信度） |
| 非票种字段数 | 72 |
| min | 0.500 |
| 中位数 | 0.916 |
| max | 0.949 |
| < 0.75（默认阈值） | 11（15.3%） |
| = 0.5（无逐字段置信度回退） | 8（全部是 `invoice_code`，见 §7 D1） |

**逐字段置信度（非票种，n = 8）**：

| 字段 | min | 中位数 | max |
|---|---|---|---|
| `amount` | 0.565 | 0.835 | 0.877 |
| `buyer_name` | 0.929 | 0.935 | 0.939 |
| `buyer_tax_id` | 0.917 | 0.929 | 0.935 |
| `invoice_code` | 0.500 | 0.500 | 0.500 |
| `invoice_date` | 0.876 | 0.918 | 0.928 |
| `invoice_no` | 0.888 | 0.912 | 0.913 |
| `seller_name` | 0.902 | 0.930 | 0.938 |
| `seller_tax_id` | 0.779 | 0.889 | 0.921 |
| `tax_amount` | 0.815 | 0.939 | 0.949 |
| （`invoice_type` 分类置信度） | 0.723 | 0.916 | 0.957 |

**读法**：

1. **置信度在这批样本上是保守的，没有「高置信度却错」的样本**——11 个低于阈值的
   字段里，8 个是 D1 的回退值、3 个是**取值完全正确的 `amount`**（最低 0.565）。
   因此按阈值分流只会**多送人工复核**，不会放进错误数据；但若按「低于 0.75 即人工」
   设计，本批会有 3/8 的**正确金额**被判为需复核。
2. **票种分类置信度有 1/8 低于 0.75**（0.723），与 D2 的粒度问题一致：分类边界
   本身就不总是自信的。
3. 与 W2-35（中位数 0.912、<0.75 占 19.4%）相比方向一致，本批 <0.75 占比略低
   （15.3%），但**样本量小（n=8）**，不构成分布结论。

## 7. 缺陷清单（**不在本任务内修复**，建议由 Master 决定是否立项）

### D1（确证缺陷）数电票的空数组字段被 `str()` 成脏值 `invoice_code`

- **现象**：8/8 票产出 `invoice_code`，值为 **2 字符非数字脏值**，8 票**完全相同**；
  该字段置信度 8/8 回退 `0.5`。
- **根因（已离线复现，零真实调用）**：提供商对该字段返回**空数组**；
  `_collect_named_fields` 展开时 `_unwrap_field` 只处理「非空数组取首元素」，空数组
  原样返回，随后 `_clean_str` 对列表做 `str()`（`str([]) == "[]"`）→ 得到非空字符串，
  于是被当作有效字段写入，且因无逐字段置信度而回退 `0.5`。用桩传输喂入
  `{"InvoiceCode": []}` 可稳定复现 `invoice_code == "[]"`、置信度 `0.5`——**该复现不
  消耗任何真实调用**。
- **影响**：
  1. **票面不存在该字段的票（数电票）100% 产出错误值**——本批污染率 8/8；
  2. 任何以 `invoice_code` 做唯一性/重复票校验或导出列的功能都会拿到脏值；
  3. 该字段永远落在阈值以下 → 每张数电票都会多一条「必填项待确认」，增加人工负担；
  4. 同类空数组字段（若其它票种也返回 `[]`）会被同样污染——本批只观察到
     `invoice_code` 一处，但**机制是通用的**。
- **建议修复方向（本任务不实施）**：在字段展开/清洗层把「空数组/空映射」视为**无值**
  （与 `None`/空白同处理），并为该场景补一条单元测试（空 `result` 值不得产出键）。
  **代码路径**：`_unwrap_field` / `_clean_str`（`app/integrations/baidu_invoice_ocr.py`）。

### D2（能力/粒度缺陷，非解析错误）`invoice_type` 无法区分业务类别

- **现象**：6 张旅客运输服务与 2 张餐饮服务的数电普票**全部**分类为 `vat_invoice`；
  分类置信度 1/8 低于 0.75。
- **影响**：W2-35 §3 提出的「人工确认必填项按票种分别设计」**不能只靠
  `invoice_type`** 落地——运输服务与餐饮服务会落到同一分支。需要引入二级信号
  （如服务项目/关键词、是否附行程单、销售方类型），属于产品设计决策。
- **注意**：这不代表分类「错」，而是**粒度不足**；本次的「数电普票 → `vat_invoice`」
  映射是本文引入的口径假设，需在后续 Issue 中确认。

### D3（阈值口径观察，非缺陷）高置信度不一定意味着可自动入账、低置信度也不代表错

- 本批 3 个**正确**的金额字段置信度低于 0.75（最低 0.565），而所有高置信度字段均正确。
  阈值分流在本批上表现为**只增加复核量**；是否调整阈值/引入人工确认策略属后续决策。

## 10. 方法与限制（n = 8，不要过度外推）

1. **样本量小**：n=8，两个业务类别（运输 6 / 餐饮 2），仅两个开票日期；**不能**据此
   推断总体准确率，也不足以支撑「≥100 张/票种」的选型报告建议。
2. **票种单一**：8 张全部为数电普票并被分类为 `vat_invoice`；W2-35 §2.2 的
   `taxi_online_ticket` snake_case 路径**本批未被触发**（云样本不再是旧式网约车票），
   其字段别名仍未在带真值样本上验证。
3. **载体不独立**：8 张中 6 张同时有 OFD 与 PDF，本任务只用 OFD；2 张仅 PDF。
   因此「OFD vs PDF 准确率差异」无法从本批得出（同票两种载体的配对比较未做）。
4. **无劣化样本**：全部为清晰电子票据（无拍照、扫描、折损、倾斜、印章遮挡），
   真实报销场景的 OCR 退化风险未覆盖。
5. **无行程单比对**：按任务约束不使用「-行程单」文件，故「发票 vs 行程单」一致性

- **凭据**：只从本地 `.env` 以环境变量装载（`BDOCR_API_KEY` / `BDOCR_SECRET_KEY`），
