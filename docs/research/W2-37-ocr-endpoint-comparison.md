## 0. 一页结论

1. **两个专用端点在本批样本上均可用且字段级与真值完全一致。** `vat_invoice` 在
   **9 个可比字段**上全部 8/8 精确一致（价税合计、不含税合计、合计税额、开票日期、
   发票号码、销方名称、销方税号、购方名称、购方税号），票种按映射口径也 8/8；
   `online_taxi_itinerary` 在**服务商、行程数、上车日期、上车时刻、总金额、申请日期**
   上 6/6 或 8/8 一致，**唯一有真值的数值弱点在「单程里程」（3/5）**。
2. **`vat_invoice` 比 `multiple_invoice` 多两个实用优势**：
   ①**直接给出不含税合计**（`TotalAmount`，无需像 W2-36 那样用 `价税合计 − 税额` 派生核对）；
   ②**旅客运输类 `Passenger*` 字段可用**（4/8 票产出，恰为真值含出行人的 4 张；出行人
   姓名 4/4 命中，证件号为**脱敏**形式，并给出出行日期 / 起终点 / 车型）。
3. **`vat_invoice` 不产出「发票代码」脏值**：8/8 票 `InvoiceCode` 为空字符串（真值=无），
   没有复现 W2-36 §7 D1 里 `multiple_invoice` 把空数组 `str()` 成脏值、置信度回退 0.5 的问题。
4. **代价：`vat_invoice` 没有字段级置信度。** 官方文档未列 `probability` 参数；本文用
   **1 次探针调用**实测该参数被**静默忽略**（响应无 `probability`，字段仍为标量），因此
   `multiple_invoice` 的「按置信度阈值分流人工复核」在本端点**无法直接复用**。
5. **票种粒度仍不足，但 `vat_invoice` 的 `ServiceType` 补上了业务类别信号**：8/8 票
   `InvoiceType` 同为「电子发票(普通发票)」，无法区分旅客运输与餐饮（与 W2-36 §7 D2
   同源问题）；但 `ServiceType` 能区分**餐饮 vs 非餐饮 8/8**（2 张餐饮 →「餐饮」，
   6 张旅客运输 →「服务」）。注意文档列出的取值含「交通」，实际客运服务返回「服务」，
   **文档与实际不一致**，消费方不得硬编码文档取值表。
6. **行程单端点是唯一能给出逐笔行程的端点**：6 份行程单 / 8 笔行程全部解析成功，
   行程数、日期、时刻、总金额全部与真值一致；`multiple_invoice` 即使识别行程单也只给
   总额与申请日期级别字段（无法核对笔数与里程）。**里程字段存在 2 处数值误识**
   （1 处数字→字母、1 处小数点丢失），是本次唯一可复现的识别质量缺陷。
7. **发现 3 个数据/能力层面的注意点（详见 §7）**：①行程单 `StartTime` / `EndTime`
   的**时间部分是占位符**（只有日期可用）；②行程单返回**明文手机号**（隐私面）；
   ③文档与真实响应存在差异（行程数组键为小写 `items`；未文档化返回 `ServiceType` 与
   逐笔 `item_provider`；`vat_invoice` 静默忽略 `probability`）。
8. **配额纪律达成**：`vat_invoice` 8 次（+1 次探针）、`online_taxi_itinerary` 6 次、
   OAuth token 1 次（缓存复用），合计 **16 次 HTTP、15 次识别调用、0 次重试、0 次失败**，
   低于 18 次上限（见 §8）。

## 4. 端点 A：`vat_invoice` 字段级准确率（n = 8，exact match）

| 归一化字段 | 响应字段 | 有真值 | 完全一致 | 缺失 | 不一致 | 准确率 |
|---|---|---|---|---|---|---|
| 价税合计 | `AmountInFiguers` | 8 | 8 | 0 | 0 | **100%** |
| 不含税合计 | `TotalAmount` | 8 | 8 | 0 | 0 | **100%** |
| 合计税额 | `TotalTax` | 8 | 8 | 0 | 0 | **100%** |
| 开票日期（ISO，归一化后） | `InvoiceDate` | 8 | 8 | 0 | 0 | **100%** |
| 发票号码 | `InvoiceNum` | 8 | 8 | 0 | 0 | **100%** |
| 销方名称 | `SellerName` | 8 | 8 | 0 | 0 | **100%** |
| 销方税号 | `SellerRegisterNum` | 8 | 8 | 0 | 0 | **100%** |
| 购方名称 | `PurchaserName` | 8 | 8 | 0 | 0 | **100%** |
| 购方税号 | `PurchaserRegisterNum` | 8 | 8 | 0 | 0 | **100%** |
| 票种（映射口径，见下） | `InvoiceType` | 8 | 8 | 0 | 0 | **100%** |
| 发票代码「是否产出」（真值=无） | `InvoiceCode` | 8 | 8 | 0 | 0 | **100%**（不产出） |

**口径与不变量**：

- **日期格式差异（不是精度问题）**：8/8 票 `InvoiceDate` 均为 `YYYY年M月D日` 形态，
  **原始形态 0/8 为 ISO**；归一化后 8/8 与真值一致。消费方必须做该归一化，否则任何
  字符串直比都会 100% 失败。
- **金额三者自洽 8/8**：`TotalAmount + TotalTax == AmountInFiguers` 在 8 票上全部成立，
  排除了「金额字段互相错位但看起来正确」的可能。
- **票种为映射口径**：8/8 票 `InvoiceType` 同为「电子发票(普通发票)」（半角括号），
  与真值「电子发票（普通发票）」（6 张另注「·旅客运输服务」）按映射计为 8/8；**该端点
  同样无法用票种区分业务类别**（见 §7 D2）。
- **字段形态稳定**：8 票的 `words_result` 键集合**完全相同**（59 键），无缺失 / 无新增；
  值为标量，需 urlencode 之外的额外处理极少。
- **发票代码干净**：`InvoiceCode` 8/8 返回空字符串 → 「不产出」，与真值「无」一致；
  **未复现** W2-36 §7 D1 的脏值问题。

### 4.1 业务类别信号：`ServiceType`（8/8 可区分）

| 真值业务类别 | `ServiceType` 取值 | 计数 |
|---|---|---|
| 餐饮服务 | `餐饮` | 2 |
| 旅客运输服务 | `服务` | 6 |

→ 「餐饮 vs 非餐饮」8/8 可分；但**文档列出的取值含「交通」，本批客运服务实际返回
「服务」**，说明该字段取值表与文档不一致，不能按文档硬编码（§7 D2）。

### 4.2 旅客运输类 `Passenger*` 字段可用性（4/8 票产出）

| 字段 | 产出票数 | 与真值核对 |
|---|---|---|
| `PassengerName`（出行人） | 4 | 4/4 命中（逐人一致） |
| `PassengerIdNum`（证件号） | 4 | **脱敏**形态（保留首尾、中间掩码） |
| `PassengerDate`（出行日期） | 4 | 3/4 与行程单上车日期一致；1 张跨零点行程票面记**次日**（§7 D3） |
| `PassengerDeparture` / `PassengerArrival` | 4 | 粒度更细（含网约车上客点 / 城区前缀 / 门牌）；真值地标**被完整包含 8/8 笔** |
| `PassengerVehicleType` | 4 | 全部为「出租车」 |
| `PassengerClass`（等级） | 1 | 仅多笔行程那张产出（3 笔各有值） |
| 其余 4 张票（真值无出行人） | 0 | 7 个 `Passenger*` 键全部为空 —— **未凭空产出**，行为正确 |

**要点**：产出与否与「票面是否真有出行人」**完全对齐（4/4 命中、4/4 未误报）**；多笔行程
时 `Passenger*` 为**逐笔数组**（`{"row","word"}`），可用于「票 vs 行程单」的逐笔核对。

## 5. 端点 B：`online_taxi_itinerary` 逐字段准确率（6 份 / 8 笔行程）

| 项 | 有真值 | 完全一致 | 说明 |
|---|---|---|---|
| 服务商 `ServiceProvider` | 6 | **6/6** | 与真值服务商一致 |
| 行程数 `ItemNum` / 数组长度 | 6 | **6/6** | 逐份笔数与真值一致（含 1 份 3 笔的多笔行程单） |
| 上车日期 `PickupDate` | 6 | **6/6** | ISO 形态 |
| 上车时刻 `PickupTime` | 8 笔 | **8/8** | `HH:MM` |
| 单程里程 `Distance` | 5 笔 | **3/5** | **2 处误识**：1 处数字→字母、1 处小数点丢失（§7 D1） |
| 单程金额 `Fare` | 3 笔（仅 1 份注明） | **3/3** | 该份 3 笔金额精确一致 |
| 总金额 `TotalFare` | 6 | **6/6** | **等于对应发票的价税合计**（跨源一致） |
| 申请日期 `ApplicationDate` | 6 | **6/6** | 等于对应发票开票日期 |
| 起终点（8 笔 × 2 字段，宽松口径） | 16 | 完整包含 **12/16**；最长公共子串占比 ≥0.6 **15/16** | 粒度差异 + 1 处**单字误识**（§7 D2） |

**读法**：

1. **金额与笔数层面完全可信**：总金额 6/6 等于发票价税合计、多笔行程笔数 6/6 正确，
   说明「行程单笔数与总额 -> 发票金额」的自动核对在本批**可以建立**。
2. **里程是唯一数值弱点**：金额被正确处理（6/6 + 3/3），里程却出现 2/5 误识，
   指向该端点对**里程这类自由数值文本缺少与金额同等的数字约束**。
3. **起终点只能做宽松匹配**：端点返回**比真值更细**的地址（上客点、城区前缀、门牌），
   精确集合相等本来就不适用；放宽到「地标完整包含」为 12/16，说明多数情况下可用，
   但存在**地名单字误识**（15/16 达到 0.6 子串占比，唯一低于者是 1 处单字错）。
4. **`StartTime` / `EndTime` 时间部分为占位符**（形如 `YYYY-MM-DD --:--`）：
   6/6 份都如此 → 只能取到日期，**不能**当作行程起止时刻（§7 D4）。
5. **文档与真实响应差异**：行程数组键在真实响应中为**小写 `items`**（文档参数表写
   `Items`，文档示例 JSON 也是小写）；响应还含文档未列出的顶层 `ServiceType`
   （取值「交通」）与逐笔 `item_provider`（本批为空串）→ 解析方必须按**真实响应**而非
   文档表解析（§7 D4）。

## 6. 与 `multiple_invoice` 基线（W2-36）的对比

**基线说明**：右侧数值全部来自 [W2-36](W2-36-baidu-accuracy-acceptance.md)（同一批 8 票，
`multiple_invoice`，2026-10-18 真实调用 8 次），**本文未重复调用该端点**。两侧均为
**聚合口径**，不列逐票值。

| 归一化字段 / 能力 | `multiple_invoice`（W2-36，n=8） | `vat_invoice`（本文，n=8） | 差异要点 |
|---|---|---|---|
| 价税合计 | 100%（`amount`） | **100%**（`AmountInFiguers`） | 同级 |
| 不含税合计 | **无该键**；派生核对 `amount − tax` 100% | **直接字段 100%**（`TotalAmount`） | 专用端点更省一步、更不易错 |
| 合计税额 | 100%（`tax_amount`） | **100%**（`TotalTax`） | 同级 |
| 开票日期 | 100%（归一化后 ISO） | **100%**（需从 `YYYY年M月D日` 归一化） | 同级；两侧都需归一化 |
| 发票号码 | 100% | **100%** | 同级 |
| 销方名称 / 税号 | 100% / 100% | **100% / 100%** | 同级 |
| 购方名称 / 税号 | 100% / 100% | **100% / 100%** | 同级 |
| 票种（映射口径） | 8/8（全部 `vat_invoice`） | **8/8**（全部「电子发票(普通发票)」） | 同级；**两者都无法区分业务类别** |
| 业务类别信号 | **无**（W2-36 D2） | **`ServiceType` 可区分餐饮/非餐饮 8/8** | 专用端点有可用二级信号 |
| 发票代码 | **0%（8/8 脏值，置信度回退 0.5）** | **不产出（8/8，无脏值）** | 专用端点无 D1 类污染 |
| 字段级置信度 | **有**（`min`/`average`；中位数 0.916；<0.75 占 15.3%） | **无**（`probability` 被忽略，§7 D4） | 生产端点唯一不可替代的能力 |
| 旅客运输 `Passenger*` | 归一化输出**无**该字段 | **4/8 票产出，姓名 4/4 命中，证件号已脱敏** | 专用端点可支撑出行人核对 |
| 行程单能力 | 仅 `total_fare` / `application_date` / `service_provider` 级别（W2-35 观察，**无带真值基线**） | — | mi 的行程单能力**未在本批做真值比对**，故只列能力差异、不列准确率 |
| 逐笔行程（时间/里程/起终点/金额） | **无**（W2-35 观察） | **8 笔全部解析，日期/时刻/金额/笔数 6/6** | 行程单端点不可替代 |
| 一次调用覆盖范围 | 「一页多票」按类型分流（W2-35） | 单张票；行程单需另调端点 | 结构不同（见 §6.1） |

### 6.1 结构差异（响应形态）

| 维度 | `multiple_invoice` | `vat_invoice` | `online_taxi_itinerary` |
|---|---|---|---|
| 顶层结构 | `words_result[]`（**数组**，一页多票 → 多项） | `words_result`（**对象**，单票） | `words_result`（**对象**，单份） |
| 每票标识 | 每项含 `type`、`probability`（分类置信度）、`left/top/width/height` | 无 `type` / 无分类置信度 / 无位置框 | 无 |
| 字段形态 | 字段值 `[{"word":…,"probability":{"min","average"}}]` | **标量**字符串（多值字段为 `[{"row","word"}]` 数组） | **标量**字符串 + `items[]`（逐笔对象，键为小写 `items`） |
| 显式不传即无的开关 | `probability=true` 生效 | `probability` 被忽略；`seal_tag=true` 才返回印章判断 | 无此类开关 |
| 多值字段 | 按类型给出 | `Commodity*` / `Passenger*` / `Transport*` / `Construction*` 逐行数组 | `items[]` 逐笔 |
| 失败形态 | 业务错误码 → 适配器稳定原因码 | 同左 | 同左 |
| 页码信息 | 未见返回 | `pdf_file_size` / `ofd_file_size` | `pdf_file_size` |
| 大小上限（文档） | 4M | **8M** | 4M |
| 文档给出 `type` 参数 | 无（按类型自动分流） | `normal`（普票/专票/电子发票）/ `roll`（卷票） | 无 |

**对接含义**：`vat_invoice` 的响应比 `multiple_invoice` **更简单**（对象 + 标量），
解析复杂度更低；但**失去**分类置信度、位置框与「一次多票」能力。`online_taxi_itinerary`
的逐笔结构需要新的解析路径（现有 `multiple_invoice` 适配器的 `taxi_online_ticket`
分支只处理总额级字段）。

## 7. 失败与缺陷清单（**不在本任务内修复**，供 Master 决定是否立项）

| 编号 | 类别 | 现象（聚合、脱敏） | 影响 | 计数 |
|---|---|---|---|---|
| **D1** | 识别质量（确证） | 行程单**里程**字段出现 2 处数值误识：1 处数字→字母、1 处小数点丢失；同份行程单的**金额**字段却全部正确 | 里程是「行程合理性/里程报销」类规则的输入，错误值会静默进入核对 | 2/5 笔（有真值样本） |
| **D2** | 能力 / 文档一致性 | ①`vat_invoice` 的 `InvoiceType` 只到「电子发票(普通发票)」，**无法区分旅客运输/餐饮**（与 W2-36 D2 同源）；②其 `ServiceType` 虽可区分（8/8），但**实际取值与文档列出的取值表不一致**（文档有「交通」，实际返回「服务」） | 不能按票设计「人工确认必填项」；不能按文档硬编码 `ServiceType` 取值 | 8/8 票同一票种值 |
| **D3** | 跨源口径差异（非识别错误） | 1 张跨零点行程：票面 `PassengerDate` 记**次日**，行程单上车日期记**当日** | 「票 vs 行程单」日期一致性校验若用严格相等会**误报**，需容忍跨零点 | 1/4 张（有出行人的票） |
| **D4** | 文档与真实响应不一致 | ①`vat_invoice` **静默忽略** `probability=true`（1 次探针：HTTP 200、键集合与标量形态不变、响应无 `probability`）→ **无字段级置信度**；②行程单行程数组键为**小写 `items`**（文档参数表写 `Items`）；③行程单返回文档未列出的顶层 `ServiceType` 与逐笔 `item_provider`；④行程单 `StartTime`/`EndTime` **时间部分为占位符**（只有日期可用） | ①置信度分流不可复用（W2-36 的人工复核策略需另设）；②解析方按文档表实现会取不到行程 | 探针 1 次；`items` 6/6；占位符 6/6 |
| **D5** | 隐私 / 数据面 | 行程单响应顶层返回**明文手机号**（11 位，6/6 份） | 该端点响应比票据端点更敏感（票据 `PassengerIdNum` 已脱敏）→ 留痕、日志、留存与脱敏必须专门处理 | 6/6 份 |

**偏差方向**：D1 是**单向的取值污染**（真值有精确值 → 端点给出错值），不会漏取，
但错误值不带任何可判别标志（无置信度，见 D4①）→ **下游无法自动识别**，只能靠
与发票金额的交叉核对发现（本批里程错误的两笔金额均正确，故金额核对**发现不了**里程错误）。

## 10. 方法与限制（n = 8 + 6，不要过度外推）

1. **样本量小**：端点 A n=8（运输 6 / 餐饮 2）、端点 B n=6（8 笔行程）；**不能**据此推断
   总体准确率，也不足以支撑「≥100 张/票种」的规模建议。
2. **票种单一**：8 张全为数电普票；专票、卷票（`type=roll`）、通行费电子普票、
   区块链发票等未覆盖。
3. **与 W2-36 同源**：两侧用同一批票、同一供应商、同一天运行，属**同源交叉验证**，
   不是独立样本复核；同日同端点的稳定性结论不成立。
4. **无劣化样本**：全部为清晰电子票据（无拍照、扫描、折损、倾斜、印章遮挡）。
5. **载体不独立**：6 张同时有 OFD 与 PDF（本任务只用 OFD），2 张仅 PDF；
   「OFD vs PDF 差异」无法从本批得出（但两组字段集合与准确率一致）。
6. **里程真值不全**：端点 B 只有 5 笔有里程真值、3 笔有金额真值 → 里程 3/5 的分母很小，
   只能作为**缺陷线索**而非比率结论；「总金额 = 发票价税合计」6/6 是更强的证据。
7. **外部服务不确定性**：结果为一次真实运行快照；有效载荷、调用次数与比较口径可复现，
   逐位取值不保证可复现。
8. **未覆盖多页**：本批 PDF / OFD 均为 1 页，未触发 `pdf_file_num` / `ofd_file_num`
   与多页合并语义。

  不入 PR、不入评论**；报告只有聚合统计，不含任何字段值、金额明细、主体标识、地名或行程。

  scratch 文件，任务结束随批次删除。
- **失败**：任一项失败只记入聚合计数（本批 0 次），不输出供应商原文。

## 13. 复现方式（不含任何敏感值）

```
# 1) 仓库外创建 scratch（如 <scratch>/46-invoices），解压所有者提供的票据压缩包
# 2) 本地 .env 提供 BDOCR_API_KEY / BDOCR_SECRET_KEY（确认已被 git 忽略），以环境变量装载
# 3) 端点 A：每票优先 .ofd，否则 .pdf（排除「-行程单」文件）→ base64+urlencode →
#    POST rest/2.0/ocr/v1/vat_invoice（form，access_token 置 URL 参数）
# 4) 端点 B：6 份「-行程单.pdf」→ 同法 POST rest/2.0/ocr/v1/online_taxi_itinerary

# 6) 结束后删除 scratch 目录（含 token 缓存与原始响应）
```
