## 2026-10-20 架构定位说明（新旧规范优先级）

本文件是早期的业务工具治理与财务导出整合计划。自 2026-10-20 起，产品定位、信任边界、运行时无关架构、任务治理和阶段路线以 [docs/AGENTMGR_STANDALONE_PLATFORM_PLAN.md](AGENTMGR_STANDALONE_PLATFORM_PLAN.md) 为准。本文件中未冲突的业务工具契约、权限校验、确认持久化、审计与 Track D 导出要求仍可作为设计参考；与新计划冲突的旧表述视为历史决策，不得当作当前实现前提。

特别是：
- AgentMgr 不再以 Hermes 为唯一或原生必需运行时；Hermes 是第一个待验证/兼容的 Runtime Adapter。
- “Agent 侧选工具”仅表示不在 AgentMgr 重复实现自然语言意图路由，并不削弱 AgentMgr 对任务必要性、优先级、责任、职权、允许/禁止能力、执行授权和审批门禁的确定性控制。
- 客户端 MCP/REST、服务端 Agent 业务工具 MCP、Runtime Adapter 控制接口属于不同信任边界；不得共用无限制管理员凭据。
- 提示词和工具描述不能强制拦截客户端本地 Shell、文件、浏览器或自有凭据。强制治理必须通过 PEP、企业资源访问控制或受控执行环境实现。

## 1 背景与目标

AiNativeERP 是一个以自然语言驱动企业业务的 AI-Native ERP 参考实现。其值得研究的部分包括受控业务工具、意图与参数 Schema、权限和风险治理、人工确认、Agent Trace，以及知识检索与实时业务数据的边界。

AgentMgr 已有独立的业务后端与相关基础能力：身份与权限、报销业务及状态机、工作流、附件受理与解析、审计、事务性 Outbox，以及 PostgreSQL 数据访问。整合工作的目的不是重写这些能力，而是明确 Agent 与业务后端之间稳定、可验证、可审计的接口，使更换 Agent 运行时、模型或渠道时不需要重写业务核心。

### 1.1 预期目标

1. 形成差距分析与复用边界，区分已有、欠缺、不需要及不宜复用的能力。
2. 建立与模型、Agent 框架和通讯渠道解耦的业务工具契约与受控执行路径。
3. 将调用记录、风险判断、审批与业务结果串联，增强可追踪性。
4. 为对外的账务数据交接提供模板驱动、可校验、可复现的导出路径。
5. 在确有需要时为知识检索建立清晰的扩展点，不提前引入向量库与模型服务。

### 1.2 非目标

- 不把 AiNativeERP 的整套 .NET ERP 合并到 AgentMgr。
- 不平行建立第二套用户、权限、报销、工作流、审计或业务数据库模型。
- 不将 Semantic Kernel、Microsoft Agent Framework、Qdrant、Ollama 或任何特定 LLM 供应商变成核心业务层的强制依赖。
- 不以通用 SQL、任意表读写、任意 Shell 命令作为 Agent 业务工具。
- 不对接金蝶或其他特定第三方财务系统；不实现自动上传/自动过账。
- 不在本计划中实现会计凭证、科目表、总账或报表引擎（属远期计划）。
- 不把敏感词黑名单或模型自我声明的风险评分当作权限控制的替代品。

## 2 实施原则

1. **业务后端是权威执行方。** 模型可以协助理解、提取字段和建议操作，但身份、参数合法性、权限、业务约束与状态转换由后端决定。
2. **沿用现有能力。** 身份、权限、报销状态机、工作流、审计、文件处理与 Outbox 优先扩展而非复制。
3. **默认拒绝。** 身份未验证、权限未命中、Schema 不匹配、参数不完整或业务状态非法时，拒绝执行或要求补充信息。
4. **副作用可控。** 写操作按风险采取草稿、明确确认、审批、幂等与审计；不得让模型调用绕过业务服务。
5. **核心层不依赖 Agent 框架。** 工具契约与执行服务由 AgentMgr 自有代码定义；Hermes、MCP、Web/API 只是调用方或适配器。
6. **契约按业务意图命名。** 用 `expense.claim.submit`、`finance.export.period`，不用 `kingdee.*` 之类供应商命名，使远期自研财务模块可替换实现而不改契约。
7. **导出是只读投影。** 导出不改业务状态、不产生会计事实；账务权威源在导入方。
8. **小步交付。** 每个阶段先有 Issue、锁定路径、验收条件与真实测试证据，再进入下一阶段。
9. **复用需可追溯。** 优先吸收设计与接口思想；确认有实质价值才复制 MIT 代码，并保留版权、许可与来源记录。

## 5 Track B：业务工具契约层

### 5.1 目标

为 Agent 调用业务能力定义稳定的工具契约与受控执行流程。工具层只描述可调用能力、校验输入、协调既有授权与服务、规范化结果；不持有业务规则或业务状态的第二份真相。

### 5.2 契约字段

| 字段 | 说明 | 约束 |
|---|---|---|
| `name` | 稳定唯一标识 | 业务域.实体.动作，如 `expense.claim.submit` |
| `version` | 工具定义版本 | 整数；语义或 Schema 变更必须升版，Trace 记录实际版本 |
| `description` | 用途与边界 | 必须写明「不适用于什么」，避免描述过宽 |
| `input_schema` | 参数 Schema | 类型、长度、范围、枚举、必填；**每个字段标 `source: model \| server`** |
| `required_permissions` | 所需权限 | 复用现有权限目录标识，不自造 |
| `scope` | 数据范围维度 | `self` / `department` / `company` / `approval_chain`，用于生成越权负向测试 |
| `risk_level` | 风险级别 | `low` / `medium` / `high` / `critical`，映射执行策略 |
| `side_effect` | 副作用 | `none` / `draft` / `state_change` / `external_call` / `file_export` |
| `confirmation_policy` | 确认要求 | `none` / `user_confirm` / `approval`；须绑定 payload hash、TTL、一次性消费 |
| `idempotency_policy` | 幂等策略 | 键来源（调用方提供或由规范化参数派生）与重复请求语义 |
| `handler` | 执行入口 | 具名标识 → 显式注册表解析；**禁止**任意导入路径或可调用对象 |
| `result_schema` | 结果规范 | 统一类别 + 机器可读错误码 |
| `audit_action` | 审计动作 | 复用既有审计事件类型与资源类型，注明是否记录拒绝 |

**逐字段 `source` 的作用**：把「LLM 只提议」变成可测约束。`employee_id`、`approver_id`、已查验发票金额等必须 `server`；`model` 字段仅限自然语言描述、意图性参数，且进入服务层前必须重新解析与校验。

**结果类别**（`result_schema`）：`ok` / `needs_more_info`（澄清）/ `needs_confirmation` / `invalid_argument` / `unauthenticated` / `forbidden` / `not_found` / `conflict` / `internal_error`。错误码复用 `app/api/errors.py` 的稳定码表（`authorization_denied`、`invalid_transition`、`validation_error`、`conflict` 等），不新造第二套。

### 5.3 推荐执行链路

```text
已验证的请求身份与上下文
          |
          v
      工具目录解析（按 name + version）
          |
          v
      参数 Schema 校验（含 source 检查：server 字段拒绝模型提供）
          |
          v
  身份 / 权限 / 数据范围（scope）校验
          |
          v
   风险策略与确认 / 审批门禁
          |
          v
  既有领域服务与业务状态机
          |
          v
  事务 / 幂等 / Outbox（适用时）
          |
          v
  统一结果 + 审计 + 执行追踪
```

具体事务顺序依据现有数据库会话、工作流与 Outbox 设计确定，不照概念图重写既有逻辑。

### 5.4 与现有模块的边界

- **身份与授权**：继续使用后端验证的 Principal 与授权服务。不得相信模型或请求体自报的 `employee_id`、角色、权限或审批人。
- **报销及状态机**：命令仍由既有报销服务与状态机执行；工具层不得自行改状态。
- **工作流**：审批任务的创建、路由、批准、驳回、补件使用现有能力，不建平行审批引擎。
- **审计**：复用既有审计服务与事件模型；拒绝的敏感操作、关键状态变化、外部调用均按既有规则记录。
- **文件与解析**：解析结果仍先进草稿或人工确认，不能直接变成已批准的业务事实。
- **Outbox 与幂等**：有通知、外部同步或异步副作用时沿用现有 Outbox、幂等键与重试边界。
- **Agent 与渠道**：Hermes、微信或其他客户端是调用方，不是授权权威；契约不得依赖某运行时内部类。

### 5.5 最小实施范围（候选，待 Track A 确定）

1. 查询当前身份有权查看的报销单及其状态；
2. 从经过验证的受理/解析结果建立报销草稿；
3. 提交报销单并触发现有工作流；
4. 查询本人有权查看的审批进度；
5. 在满足权限、数据范围与禁止自审规则时，调用既有审批流程；
6. 在权限范围内触发导出（Track D 的 `finance.export.period`）。

不因示例列出某项就自动扩大范围。

### 5.6 已决策 B-1：谁负责「选工具」（2026-10-17 所有者）

**决策：选项 (a) —— Agent 侧决定使用哪个工具**（协议与运行时无关），AgentMgr 不重复实现自然语言意图路由；但 AgentMgr 必须确定性控制任务是否值得执行、优先级与责任归属、允许/禁止能力、执行 Grant、审批门禁与实际 PEP。后端不是无条件工具转发器。

| 选项 | 结论 | 理由 |
|---|---|---|
| (a) Agent 侧选工具，AgentMgr 治理执行条件 | **采用** | 不重复造编排器；运行时可替换，但权限和执行门禁由服务端决定 |
| (b) 后端做域/意图路由 | 否决 | 等于重复建设编排/意图路由层，与本项目不重复造轮子、保持核心简单的目标冲突，维护成本最高 |
| (c) 混合：后端提供候选检索，Agent 决定 | 暂不采用 | 两处状态，契约与测试都要覆盖；若 (a) 出现实际路由质量问题再评估 |

**配套约束（必须同时落地）**：

1. 工具描述互斥，并写明「不适用于什么」；
2. `needs_more_info` 为一等结果，歧义必须追问，不得猜测后执行；
3. 在 `app/tests/qa/` 建立路由负样本：同一句话不得同时命中两个写操作工具；
4. 后端仍对每个请求重新校验身份、权限、`scope` 与状态，不因「Agent 已选定」而放行。

对应章程 D8。

### 5.7 已决策 B-2：确认请求如何持久化（2026-10-17 所有者）

**决策：选项 (a) —— 新增轻表**（暂定 `tool_confirmations`），持久化待确认的写操作请求。理由：微信入口是异步的，用户可能在数分钟后回复「确认」，待确认状态不能只存在于 Agent 进程或会话上下文。

| 选项 | 结论 | 理由 |
|---|---|---|
| (a) 新增 `tool_confirmations` 轻表 | **采用** | 语义清晰，需一次迁移 |
| (b) 复用 workflow 审批实例 | 不采用 | 审批语义被稀释，中风险「确认」与高风险「审批」混在一起 |
| (c) 不持久化，靠会话 | 否决 | 换会话/换进程即丢，且无法防重放 |

该表至少包含：参数快照（规范化 JSON）、payload SHA-256、发起人、渠道绑定、`tool_name` 与工具版本、状态、TTL（建议 15 分钟）、创建与消费时间。

**执行约束**：

1. 确认绑定**规范化参数 hash**，hash 不符即拒绝（防确认后被替换）；
2. 一次性消费，重复确认第二次拒绝；
3. TTL 过期即拒绝，需重新发起；
4. 执行前重新校验权限与状态，不得因「已确认」跳过状态机；
5. 建表与实现放在 Track B 的确认类 Issue，不与只读工具切片混在一起。

### 5.8 测试与验收标准

1. 有权限的合法请求调用正确的领域服务，结果符合 `result_schema`。
2. 未认证、已解绑渠道身份、伪造身份、无权限、越出 `scope` 的请求全部拒绝。
3. 参数缺失、类型错误、越界数值、未知工具名、未知操作被拒绝或进入 `needs_more_info`。
4. 无效状态转换、自审审批、重复提交、并发重复与重试不产生错误状态或重复记录。
5. **静态闸门**：`app/agent/tools/**` 不得 import `sqlalchemy` 或 `app.db.session`（AST 扫描测试）。
6. **每个工具至少 1 正向 + 4 负向**（未认证 / 越权 / 越数据范围 / 非法状态），与 `app/tests/qa` 负向矩阵风格一致。
7. **审计断言**：每次执行断言审计行数 == 1，`actor_id` 为已验证人员；拒绝路径同样留痕。
8. 需确认的写操作，在确认完成前不产生最终副作用；payload hash 不符、TTL 过期、重复确认均被拒绝。
9. 工具目录与适配器可在不启动 Hermes、不连接模型的条件下独立测试。
10. 现有测试不删除、不跳过、不弱化；提供真实命令、退出码与当前提交 SHA。
11. 不新增不必要依赖；确需新增时在 Issue 说明理由、替代方案与维护成本并获批准。

### 5.9 禁止事项

- 不实现万能 `execute_sql`、`query_any_table`、`update_any_entity` 或任意 Shell 工具。
- 不复制演示角色守卫，不以工具名黑名单代替业务权限校验。
- 不让工具处理器绕开领域服务直接读写数据库。
- 不把 LLM 输出的金额、日期、员工 ID、审批结果或风险分数视为权威事实。
- 不默认引入完整 RAG 栈、第二个 Agent 编排框架或第二套审批系统。

## 6 Track C：可观测性与知识能力

### 6.1 A 项：AI 操作可观测性

**目标**：从一次业务请求追踪到工具调用、参数校验、权限判断、确认/审批、领域服务执行、最终结果与审计记录。

**关联字段**（最小必要）：`request_id` / `trace_id`；已验证操作主体引用与渠道类型（不存外部身份原文）；`tool_name` 与工具定义版本；执行阶段；校验结果、拒绝原因码、风险策略结果；审批/工作流实例 ID；业务资源类型与 ID；结果类别、耗时、重试与幂等状态、外部调用状态。

**禁止**：写入访问令牌、密码、API Key、完整票据内容或不必要的个人信息；记录模型输入/输出前必须执行数据最小化与脱敏。

**验收**：同一操作的工具执行、审批、状态与审计可通过稳定标识关联；可区分成功、参数拒绝、权限拒绝、等待确认、审批拒绝、业务冲突、外部失败与内部错误；Trace 不替代正式审计；关键拒绝与失败路径有测试，且验证日志中无已知秘密。

### 6.2 B 项：业务知识检索（条件性）

**强制边界**：RAG 只用于非结构化知识（制度、流程、指南）；实时业务事实必须查业务服务；回答须带来源或明确「未检索到」；导入/更新/删除需鉴权与来源记录；送入外部模型或 Embedding 前执行分类、最小化与脱敏；优先定义与向量库无关的 `KnowledgeSearch` 接口。

**立项判断条件**（满足其一并经批准）：制度文档数量已影响效率；关键字搜索无法满足语义需求；来源、更新责任、权限、保留期与数据处理方式已明确。

**验收（实施时）**：可重复的检索质量测试（应命中、不应命中、相似不相关、过期文档）；回答保留来源引用；知识检索与业务查询走不同接口与权限路径；未授权用户不能经检索越权取数；重建失败或 Embedding 不可用时有明确恢复行为。

## 7 Track D：财务对外口径（Excel 导出）与远期财务模块

### 7.1 目标与非目标

**目标**：按所有者提供的模板导出特定格式 `.xlsx`，供其他财务系统导入；导出可校验、可复现、可审计。

**非目标**：不自动上传、不自动过账、不生成会计凭证、不维护科目表与总账、不对接金蝶等特定系统。

### 7.2 导出契约（模板驱动）

- **模板标识**：`template_id` + `template_version` + 模板文件 SHA-256；任何列或口径变化必须升版，不改历史版本。
- **映射定义**：字段 → 列、列顺序、表头、数据起始行、日期/金额格式、期间与币种口径、单据号规则、合计行规则。
- **模板存放**：与 O6 一致，模板文件置于仓库外受控目录；仓库内只放映射定义、合成样例与校验用例。
- **未提供模板时**：只交付 loader / validator / mapping engine，用**合成模板**测试；禁止猜测列名与列序，禁止把参考项目或某财务软件的格式当作默认模板。
- **导出范围**：至少支持「单张报销单」与「按期间批量」两种，由 `template_id` 区分（同一模板不得混用两种粒度）。

**与现有导出的关系**：`app/documents/export.py` 现有 `render_claim_pdf` / `render_claim_xlsx` 是**供人阅读与归档的版式导出**，不复用于财务导入；Track D 是**机读投影**，但复用 `app/documents/storage.py` 的存储、哈希校验、下载鉴权与保留期机制，并复用 `app/expense/money.py` 的金额口径。两者不得互相替代，也不得在同一个函数里用参数切换。

### 7.3 校验与失败行为

- 行数、笔数、金额合计（`Decimal` 到分）与数据库对账；任一不符即 **fail closed**，不产出文件。
- 重复单据号、跨期数据、超出授权范围的记录不得进入导出。
- 每次导出生成 **manifest**：期间、模板版本、记录 ID 集合、行数、金额合计、文件哈希、导出人与时间。
- 幂等：同期间 + 同模板版本重复导出，manifest 可复现；仅当模板不含时间戳时承诺字节一致。

### 7.4 安全与合规

- 单元格注入防护：以 `=`、`+`、`-`、`@` 开头的文本必须转义；只产出 `.xlsx`，不产出 CSV，不使用宏。
- UTF-8；文件下载需鉴权；设定保留期；导出行为写审计。
- 导出文件含个人信息与金额，按 W0-5 分类处理，不写入日志与 Trace。

### 7.5 远期财务/ERP 模块的接缝

1. **契约先行**：工具与导出均以业务语义命名，远期新增 `app/finance/` 时以新实现替换「导出适配器」，契约不变。
2. **单一权威源**：同一期间只能有一个账务权威源。启用内部账务前必须显式决策迁移，禁止与外部导入并行双账。
3. **不提前建模型**：在确认需求与迁移方案前，不引入科目表、凭证、期间关账等模型；先做投影与导出。
4. **迁移另立计划**：历史数据迁移、期初余额、对账规则不在本计划范围内。

### 7.6 验收标准

- 合成模板 + 合成数据端到端跑通：选择期间 → 生成 → 校验 → 下载 → 审计可查。
- 篡改一笔金额后校验失败且不产出文件（不得产出「看起来能用」的半成品）。
- 同一期间重复导出 manifest 一致。
- 未授权角色不可导出；导出不改变任何报销单状态（断言前后状态一致）。
- 模板缺失或版本不匹配时返回明确错误码，不静默降级为默认格式。

## 8 跨 Track 门槛

1. Issue 写明目标、允许路径、禁止路径、依赖、测试命令与可观察验收条件。
2. 派发前按 Agent-Orchestration 规则登记活动任务与路径锁。
3. Execution Agent 只提交实现与证据；Reviewer 独立审查；只有 Master 按门禁批准与合并。
4. 审查与 CI 证据必须对应待合并 PR 的当前 head SHA。
5. 测试结果须提供真实命令、退出码与可核验输出。
6. 不删除或削弱既有断言。
7. 新依赖、数据库迁移、权限语义改变、公开 API 契约变化、安全边界改变须在 Issue 说明并获批准。
8. Track 完成后更新任务记录与会话交接，写明合并 SHA、验证结果、遗留项与下一入口。

| 4 | Track B：负向测试与审计关联 | 2（可与 3 合并） | 越权、伪造身份、重复执行、非法状态、确认绕过；静态闸门 |

## 10 风险与应对

| 风险 | 应对措施 |
|---|---|
| 与现有业务服务重复 | Track A 先映射；工具层只做契约、协调与验证 |
| Agent 身份或参数被伪造 | 后端 Principal；`source: server` 字段拒绝模型提供；服务层重新解析并校验 `scope` |
| 误执行或重复执行 | 草稿/确认/审批策略、幂等键、状态机、事务与负向测试 |
| 确认被重放或确认后备替换 | payload hash + TTL + 一次性 + 执行前复检 |
| 审计链路断裂 | 统一关联请求/工具/工作流/资源标识；拒绝路径同样留痕 |
| 导出模板口径漂移 | 模板版本化 + SHA-256 + 对账校验 + 只升版不改历史 |
| 双账并存 | 单一权威源；内部记账启用前显式迁移决策 |
| 远期 ERP 范围膨胀 | 先投影与导出，不建科目/凭证；每个 Issue 单一目标 |
| 引入过多基础设施 | 不默认引入 Qdrant/Ollama/MCP 服务 |
| 绑定单一 Agent 框架 | 契约与执行层框架无关，适配器在边界层 |
| 复制外部项目不成熟代码 | 先借鉴设计；复制须逐文件审查、测试并保留许可记录 |

## 11 最终建议

按 **Track A 评估 → Track B 最小工具契约 → Track C 可观测性 → Track D 导出机制** 推进，Track D 的首个模板与 Track C 的知识检索分别在模板就绪与需求成立时启动。

Track B 是整合核心：让后端拥有稳定、框架无关的工具接口与治理能力。Track D 是当前唯一确定的对外账务口径，必须先做到「可校验、可复现、不改账」。远期的自研财务/ERP 通过同一契约接替实现，而不是另起一套系统。

本文件是待审的规划文档，不表示上述 Issue 已建立、代码已实现或任何 Track 已通过验收。所有实施必须按 AgentMgr 当前 Agent-Orchestration（GitHub 版）规则执行。
