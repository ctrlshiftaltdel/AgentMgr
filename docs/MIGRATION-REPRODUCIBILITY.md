# 迁移可复现性：迁移不得读取活动应用代码

- 日期：2026-10-16
- 范围：Alembic 迁移链的确定性（可复现性）约定
- 触发：W1-13 复核发现 `0003_permission_catalog` 读取活动代码（Issue #2 / 任务 W1-16）
- 用途：把「迁移是历史快照、不是活动代码的投影」这一约定与影响评估固化为仓库内可追溯文档

## 1 结论摘要

- **约定（硬要求）**：已应用的迁移**不得**从 `app.*`（或任何会被持续编辑的活动代码）读取要写入的数据（目录、枚举、常量、矩阵）。迁移必须自带它所声称的、写死在版本内的**冻结数据**。需要跨迁移共享的定义，应复制进每个迁移，而不是 `import` 应用的「单一来源」。
- **本次处置**：`migrations/versions/0003_permission_catalog.py` 从「读取 `app.identity.permissions` 当前目录」改为**冻结快照**（自带当时目录：7 角色 / 19 权限 / 31 映射），且不再 import 任何 `app.*`。方案选择与理由见第 3 节。
- **最终状态不变**：全新库 `upgrade head` 与既有库 `upgrade head` 均为 20 权限 / 32 映射（既有库的 `alembic_version` 已越过 0003，永不重跑，改其代码不影响既有库）。
- **未决/顺延项**：`0009_perm_alignment` 仍读取 `app.identity.permissions`（见第 5 节），本任务按 Issue 范围未改，已登记为后续项。

## 2 问题与影响评估（验收标准 1）

现状（改动前）：`0003` 的 `upgrade` 调用 `app.identity.seed.seed_permission_catalog`，该函数从 `app.identity.permissions`（应用的「单一来源」）读取**当前**目录。后果有三：

### 2.1 全新库与既有库的中间状态不一致

- **既有库**：历史执行 `0003` 时目录为 19/31，故 0003 之后停在 **19/31**；随后 `0009_perm_alignment` 增量补 `(audit, read, company)` 权限 + `finance_lead` 授权 → **20/32**。
- **全新库（改动前）**：执行 `0003` 时目录已是 20/32，故 0003 直接写入 **20/32**，`0009` 变成幂等 no-op → **20/32**。
- 结论：**最终状态一致（20/32），但中间状态不一致（19/31 vs 20/32）**。即「在 revision 0003 处数据库应长什么样」没有唯一答案，取决于迁移执行时的工作树。任何依赖中间态的可复现构建、审计或差分比对都不可靠。

### 2.2 目录再次变更时 0003 的行为会追溯改变

- 若将来 `app.identity.permissions` 再变（例如新增权限编号 21、或调整矩阵），**重放**链到 0003 的库会写入新的目录内容，而**已经**迁移过的库仍停留在旧内容；两者的最终状态会由「是否有后续迁移补差」这一偶然因素决定，无法从迁移历史本身推出。
- 这是「历史漂移」的本质：已发布迁移的语义被后续对活动代码的编辑**追溯改写**，违反「不得改写已应用迁移的历史语义」的迁移政策（见 `ORCHESTRATION-PROJECT.md`）。
- 本次 W1-13（19/31 → 20/32）本身就是这个缺陷的第一次真实发作：`0003` 的作者意图是「写入 PLAN §9 当时的目录」，但代码却写成了「写入读取时的目录」。

### 2.3 downgrade 链的可靠性

- 改动前 `0003` 的 `downgrade` 调用 `clear_permission_catalog`，其删除范围同样来自**当前**目录：删除「当前目录定义了、且数据库里存在」的角色名与权限三元组。
- 若目录已被编辑（增/删/改三元组），`downgrade` 可能：
  - **删不掉**当初由 0003 写入、但已从当前目录移除的行（留下残留，无法干净回到 0002）；
  - 或**误删**本不该由 0003 负责的行（若当前目录包含了后续迁移写入的行）。
- 结果：`0003` 的升级与回滚**不再对称**，`downgrade base` 的「干净回到 0002」只能靠巧合维持。

## 3 方案选择与理由（验收标准 2）

Issue 给出两案：

- **方案 A**：把 0003 改为冻结快照（显式列出当时的 19 权限 / 31 映射）。
- **方案 B**：不改行为，仅在迁移 docstring 与部署文档中记录该特性与影响。

**选定方案 A（冻结快照）。** 理由：

1. **对目标（消除历史漂移）是实质解决，而非记录问题。** 第 2 节三项影响的根因只有一个——迁移读了活动代码。方案 B 承认漂移存在却仍让它留在线；方案 A 直接消除根因。
2. **考古证据充分、可精确重建。** `git show c3f999e^:app/identity/permissions.py` 逐字显示当时目录为 7 角色 / 19 权限 / 31 映射；快照可逐字照录，不引入猜测。0003 的创建提交 `b3aa87d` 即该 19/31 版本，冻结的正是「0003 作者当时看到的内容」。
3. **不改最终状态、不影响既有库。** Alembic 版本链保证既有库不会重跑 0003；冻结快照 + `0009` 增量使全新库与既有库最终同为 20/32。
4. **downgrade 恢复对称。** 冻结集合使得 upgrade 写入的行与 downgrade 删除的行严格一致，`downgrade base` 可确定性干净回到 0002。

实现要点（已在 0003 落地）：

- 自带冻结常量：`_FROZEN_ROLES`（7 角色）、`_FROZEN_PERMISSIONS`（编号 1..19 的三元组）、`_FROZEN_ROLE_PERMISSION_NUMBERS`（31 映射）；仅 `import sqlalchemy` 与 `from alembic import op`，**不 import 任何 `app.*`**。
- 通过 `op.get_bind()` 直接执行 SQL，语句并入 Alembic 的迁移事务，无需显式 commit。
- **幂等**：`upgrade` 先查后插（角色按 `name`、权限按 `(resource, action, scope)`、映射按 `(role_id, permission_id)`）；`downgrade` 只删除冻结集合内的行。因此 upgrade/downgrade 往返（含 roundtrip 测试的 `downgrade base` → `upgrade head` 循环）可重复且安全。

## 4 影响范围与不变式

- **既有库**：`alembic_version` 已越过 0003，永不重跑；本改动对其数据无影响。不为既有库写任何数据修复。
- **全新库**：0003 写 19/31 → `0009` 补 20/32 → head 为 20/32，与既有库一致。
- **应用层不变**：`app/identity/seed.py`、`app/identity/permissions.py` 仍是应用层「单一来源」与幂等工具，供运行时/测试使用；本约定只约束**迁移**不得读取活动代码，不改变应用层职责。
- **回归防护**：`app/tests/test_migrations.py` 增加断言——在 0003 处目录计数恰为 7/19/31、到 head 恰为 7/20/32；并静态断言 0003 不 import 任何 `app.*`。

## 5 未决 / 顺延项

- **`0009_perm_alignment` 仍读取活动代码**：其 `upgrade` 从 `app.identity.permissions` 读取编号 20 的三元组与 `finance_lead` 授权（并断言目录与迁移一致）。严格地说，它同样属于「迁移读取活动代码」。本任务按 Issue 授权范围**未改** 0009（Issue 明确「本任务不要求改 0009」）。差异与风险已如实记录于此，是否冻结 `0009` 由后续任务决定。
- 约定落地后，**新增迁移**应遵守第 1 节硬要求：需要共享定义时复制进迁移，而非 import 应用代码。
